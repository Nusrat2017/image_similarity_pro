1. Project Overview
Goal: Find the images in a database that are most similar to a query image.

Current approach (3-stage ensemble pipeline):
Stage 1 — Deep Learning (content/semantic similarity)
	- Uses a pre-trained ResNet18 model to extract a feature vector per image.
	- Filters the database down to the most content-similar candidates.

Stage 2 — Perceptual Hash (fast structural similarity)
	- Uses average hash (aHash) packed into bytes.
	- Computes Hamming distance only on the Stage-1 candidates.

Stage 3 — ORB (keypoint/geometric similarity)
	- Uses OpenCV ORB + BFMatcher + ratio test.
	- Adds a geometry-based score and improves robustness to rotation/crop.

Final ranking:
	- Combined score = ~33% Deep + ~33% Hash + ~34% ORB

Why this works:
	- Deep features capture “what” is in the image.
	- Hash captures global structure quickly.
	- ORB captures local geometry and keypoint matches.

Key scripts / modules:
	- build_index.py      → builds/updates the index files
	- search.py           → main entry point to run a search (includes auto-indexing)
	- search_engine.py    → core 3-stage search pipeline and scoring
	- utils.py            → feature extraction + hashing + ORB utilities
	- negative_search.py  → detects “no good match” and shows warning popup
	- visualization.py    → side-by-side comparison + difference heatmap

Data folders:
	- image_database/stored_image/  → image database
	- test_image/                   → query images
	- index/                        → generated index artifacts


2. Indexing: Building / Updating the Index
Indexing happens when you run build_index.py (or automatically from search.py).

2.1 Collect image files
	- utils.iter_images(folder) walks the database recursively and returns supported image files.

2.2 Smart incremental indexing (rename-aware)
	- If index files already exist, build_index.py loads:
			- index/paths.jsonl
			- index/hashes.npy
			- index/deep_features.npy
	- For each current image:
			- If the absolute path is already in paths.jsonl → reuse stored hash + deep features.
			- Else, compute the hash and compare to existing hashes → if identical, treat as rename and reuse features.
			- Else, treat as a new image → compute deep features + hash.
	- Images missing from the folder are implicitly removed from the rebuilt index.

2.3 Feature extraction details
	A) Hash features (utils.phash_packed_bytes)
		 - Uses PIL to open image and (optionally) resize.
		 - Uses imagehash.average_hash(img, hash_size=...).
		 - Packs bits into uint8 bytes using np.packbits (fast Hamming comparisons).

	B) Deep features (utils.extract_deep_features)
		 - Uses torchvision ResNet18 (ImageNet weights).
		 - Removes the final classification layer to get an embedding.
		 - Normalizes the vector so cosine similarity is just a dot product.

2.4 Index outputs (index/ folder)
	- paths.jsonl         → one JSON object per line: {"path": "..."}
	- hashes.npy          → (N, B) uint8 packed hashes
	- deep_features.npy   → (N, 512) float32 deep embeddings (ResNet18)
	- meta.json           → index configuration (count, hash_size, max_side, etc.)
	- backup.jsonl        → optional extra output (if present in your workspace)


3. Searching: Running a Query
Searching is typically run via search.py.

3.0 Auto-indexing (search.py)
	- search.py calls build_index.needs_reindex(db_folder, index_folder).
	- If new/deleted/renamed images are detected, it rebuilds the index before searching.

3.1 Query content analysis (optional, informational)
	- search.py calls utils.classify_image_content(query_path, top_k=5).
	- Prints the top ImageNet labels and confidence.
	- This does not affect ranking; it helps interpret what the model “sees”.

3.2 Stage 1 — Deep learning content filtering (search_engine.py)
	- Loads index/deep_features.npy as a memory-mapped array.
	- Extracts deep features for the query.
	- Computes cosine similarity via dot product against all stored features.
	- Keeps the top K candidates (candidates parameter, default ~100).

3.3 Stage 2 — Hash refinement on candidates
	- Computes query hash.
	- For each candidate, computes packed-byte Hamming distance using a fast bit-count lookup table.
	- Converts distance to a similarity percentage.

3.4 Stage 3 — ORB scoring on candidates
	- Runs ORB matching between query and each candidate.
	- Produces orb_score_pct per candidate.

3.5 Final combined score and ranking
	- combined_score = 0.33*deep_score_pct + 0.33*phash_similarity_pct + 0.34*orb_score_pct
	- Results are sorted descending by combined_score.


4. Negative Search (No-Match Detection)
Implemented in negative_search.py.

What it does:
	- If the best combined_score is below a threshold (default 50%), it flags a “negative match”.
	- Prints a console warning.
	- Optionally shows a red OpenCV popup explaining that the query likely does not exist in the database.


5. Visualization: Side-by-side + Difference Heatmap
Implemented in visualization.py.

What it shows:
	- Query image and best match side by side.
	- If similarity < 100%, it also shows a difference heatmap.
	- Matching areas are tinted green, differences outlined in red.


6. Typical Usage
1) Build/update index (manual):
	 - python build_index.py

2) Run a search (auto-indexing + scoring + visualization):
	 - python search.py

To change the query image, edit the variables near the top of search.py:
	- query_path
	- limit
	- filter_size


7. Notes / Practical Considerations
- The index/ folder contains large generated files (especially deep_features.npy). If you want smaller Git commits, consider ignoring index/ and rebuilding locally.
- Deep feature extraction may download ResNet18 weights the first time (requires internet unless already cached).
- OpenCV GUI windows (cv2.imshow) require a desktop session; they won’t display in headless environments.
